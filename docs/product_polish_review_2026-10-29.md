# Product polish review — 29 October 2026

**Decision:** Spend the short pre-deployment window on trustworthy customer numbers, safe alert setup, and a focused first-use experience. Keep DigitalOcean provisioning and public-server acceptance for the planned production sprint.

## Evidence and limits

Reviewed Hub `main` at `200c011`, Gateway `main` at `f2f7f84`, the current project status, the three-scenario CM4 replay audit, active Django views/forms/templates, the template catalog, and the marketing inquiry implementation. A read-only pass in the running in-app browser inspected the one-device Command Center, empty Shared Links list/form, and blank Alert Rule form; it did not create or change records. The browser confirmed that a new alert begins with Enable Rule and Email notification checked, matching a local Django form inspection (`is_active=True`, `notify_email=True`). No CM4 run or customer hardware was used in this pass. The old static `templates/web/about.html` placeholder form is not the served Wagtail About page; the active marketing lead form posts to `support:sales_inquiry` and has tests.

## Ranked product backlog

| Priority | Customer problem and evidence | Recommended outcome and acceptance |
| --- | --- | --- |
| **P1 — correct energy truth** | `apps/telemetry/services.py:get_site_summary_stats` sums hourly **average watts** and divides by 1,000, then the active Site page labels the result **Consumption Today (kWh)**. This does not integrate power over time, ignores missing coverage and site time zone, and only recognizes `active_power` even though the documented energy catalog uses keys such as `active_power_total`. The same function sums buckets from the previous hour as **Current Demand**, which can be stale or count more than one bucket. | Derive energy from a qualified cumulative import-energy counter where available, or integrate a bounded, sufficiently covered power series. Expose coverage/estimation and last-sample time; show unavailable when the inputs cannot support a trustworthy number. Current demand must use a recent, eligible mapped reading. Test gaps, reset/rollover, multiple meters, site-local day boundary, and key variants against hand-calculated fixtures before showing kWh. |
| **P1 — repair public Shared Links** | `apps/dashboard/public_views.py` passes the same `stats` dictionary (`daily_kwh`, `current_power`) to the public template, but `templates/dashboard/public/public_dashboard.html` reads `total_devices`, `total_kwh`, and `active_alerts`. Device count can render blank, energy defaults to zero, and a site with active alerts can show a contradictory **No active alerts** pill. The link currently exposes every site and active alert in the team; the browser confirmed creation is inactive by default, but password and expiry remain optional when enabled. | Use one explicit, tested public-summary contract with accurate site count, alert state, and qualified energy display. Then add a site/audience preview before activation; consider a site-scoped share option for external viewers. Browser-check password, expiry, revocation, and tenant scope before an investor/customer link is issued. |
| **P1 — safe alert creation** | A blank `AlertRuleForm` initializes `is_active=True` and `notify_email=True` from the model defaults, while the form says the customer can save and enable later. Preset links override both to false, so the two entry paths behave differently. The reading picker is now mapped and unit-aware, and recipient validation prevents enabled email/WhatsApp without recipients; those are already fixed. | Make *every* new rule start paused with notifications off unless the customer deliberately enables them. Show the selected reading's unit, recent example value and a final summary of threshold, duration, recipients and actions. Browser-test blank creation, preset creation, edit and activation, including no automatic rule creation during onboarding. |
| **P2 — first device experience** | The one-device Command Center still gives full fleet space to Asset Mix and zero-value Maintenance/Automation cards. Device detail repeats latest readings above their widget cards. Prior customer-browser audit found this sparse/repetitive; the current panel registry and Device template retain the pattern. | For one site/device, lead with its main reading, sample age, short trend and one next action (for example, configure monitoring). Keep fleet panels for multi-site accounts. Check 390px mobile and keyboard navigation in the browser. |
| **P2 — governed changes after setup** | Customer Device Edit is now safely limited to rename, with copy directing customers to support for deployed connection/mapping changes. There is no guided revision, live re-test, customer confirmation and rollback path for an installed device. | Design a scoped change workflow that preserves the active map until a new revision passes read-only validation and approval. Implement after agreeing the first customer equipment/configuration cases; avoid a rushed general editor in this two-day window. |
| **P2 — exact-model template trust** | Seven energy maps are importable OEM-documented drafts, not field-verified; live source comparison and CT/PT, wiring, firmware and direction checks remain outstanding. Team-owned map revisions and consented publication are now implemented. | Prepare a concise first-customer compatibility worksheet and select one likely meter family for physical qualification. Do not promote draft maps or claim plug-and-play for an exact model without field evidence. |

## Suggested two-day sequence

1. **Day 1:** Fix the energy summary contract and public Shared Link display with deterministic numeric fixtures and a read-only customer-browser check. If reliable kWh cannot be derived from the available data, hide the number and explain what input is missing.
2. **Day 2:** Make alert creation paused by default, add a short enable/review moment, then simplify the one-device Command Center and remove duplicate Device readings if time permits. Run a customer-browser pass on desktop and phone width, including keyboard-only navigation.

For the later production sprint, retain the existing public-server gates: tenant isolation, external alert receipt, broker/database restore, exact-device qualification and the intermittent Laptop 2 port-502 investigation. The source review does not clear those gates.
