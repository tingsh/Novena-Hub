# Product polish review — 29 October 2026

**Decision:** Spend the short pre-deployment window on trustworthy customer numbers, safe alert setup, and a focused first-use experience. Keep DigitalOcean provisioning and public-server acceptance for the planned production sprint.

## Evidence and limits

Reviewed Hub `main` at `200c011`, Gateway `main` at `f2f7f84`, the current project status, the three-scenario CM4 replay audit, active Django views/forms/templates, the template catalog, and the marketing inquiry implementation. A read-only pass in the running in-app browser inspected the one-device Command Center, empty Shared Links list/form, and blank Alert Rule form; it did not create or change records. The browser confirmed that a new alert begins with Enable Rule and Email notification checked, matching a local Django form inspection (`is_active=True`, `notify_email=True`). No CM4 run or customer hardware was used in this pass. The old static `templates/web/about.html` placeholder form is not the served Wagtail About page; the active marketing lead form posts to `support:sales_inquiry` and has tests.

## Ranked product backlog

| Priority | Customer problem and evidence | Recommended outcome and acceptance |
| --- | --- | --- |
| **P1 — correct energy truth** | `apps/telemetry/services.py:get_site_summary_stats` sums hourly **average watts** and divides by 1,000, then the active Site page labels the result **Consumption Today (kWh)**. That arithmetic implicitly treats every bucket as a full hour even with partial/missing data, ignores site time zone, and only recognizes `active_power` even though the documented energy catalog uses keys such as `active_power_total`. The same function sums buckets from the previous hour as **Current Demand**, which can be stale or count more than one bucket. | Derive energy from a qualified cumulative import-energy counter where available, or integrate a bounded, sufficiently covered power series. Expose coverage/estimation and last-sample time; show unavailable when the inputs cannot support a trustworthy number. Current demand must use a recent, eligible mapped reading. Test gaps, reset/rollover, multiple meters, site-local day boundary, and key variants against hand-calculated fixtures before showing kWh. |

The reading picker is now mapped and unit-aware, and recipient validation prevents enabled email/WhatsApp without recipients; those are already fixed. | Make *every* new rule start paused with notifications off unless the customer deliberately enables them. Do not promote draft maps or claim plug-and-play for an exact model without field evidence. |

## Suggested two-day sequence

1. **Day 1:** Fix the energy summary contract and public Shared Link display with deterministic numeric fixtures and a read-only customer-browser check. If reliable kWh cannot be derived from the available data, hide the number and explain what input is missing.
2. **Day 2:** Make alert creation paused by default, add a short enable/review moment, then simplify the one-device Command Center and remove duplicate Device readings if time permits. Run a customer-browser pass on desktop and phone width, including keyboard-only navigation.

For the later production sprint, retain the existing public-server gates: tenant isolation, external alert receipt, broker/database restore, exact-device qualification and the intermittent Laptop 2 port-502 investigation. The source review does not clear those gates.

## Expanded Hub-wide review — 30 October 2026

This pass traced the active customer routes and templates for account entry, role-based navigation, sites/Gateways/devices, onboarding and the template library, telemetry and exports, alerts, Shared Links, maintenance, automations, Business Impact, support, and the marketing-to-app handoff. It reviewed current Hub code on the documentation branch at `042d482` (application code identical to `main` at `200c011`). Django's local `manage.py check` completed with four existing local-settings/deprecation warnings. The Hub was not serving on `localhost:8000` after this desktop start, so **the new findings below are code-confirmed or clearly marked for browser verification; they are not claims of a fresh live customer replay**. No customer records, Gateway configuration, or production services were changed.

Several previous protections are present and should be preserved: new operational automations are initialized paused by `AutomationCreateView.get_initial`, their conditions/actions are checked before activation, and Business Impact tests cover site-limited report access. The findings below focus on remaining gaps rather than repeating the six items above.

| **P1 · site-limited roles** | `SiteMembershipAccess` describes a membership site boundary, and `has_permission(..., site=...)` enforces it when a site is passed. The shared `PermissionRequiredMixin` calls the permission decorator **without** a site; `SiteListView`, `DeviceListView`, `DeviceDetailView`, `AlertListView`, and maintenance lists then query the whole team. Business Impact explicitly filters by site, showing a different access model. A site-limited member can therefore reach other sites' monitoring/work data through these team-level routes if that membership feature is used. ### Two-day execution recommendation after this deeper pass

1. **First clear trust boundaries:** Verify/fix site-limited membership access if that role will be offered to the first customers, and block public contractor links from closing tickets. These outrank visual polish. Add focused role/HTTP tests before any pilot invitation.
2. **Then fix customer-visible data:** Correct the Site energy calculation and Shared Link contract from the first review, plus history/chart/export coverage and the Shared Link alert value. Show “unavailable” or “partial” honestly where the underlying data cannot support a number.
3. **Use remaining time on workflow friction:** Make alert creation paused by default, repair the maintenance template editor and schedule validation, then align ticket notifications, sidebar permissions, severity copy, and support acknowledgement. Finish with a customer-browser pass on a running Hub and at mobile width. The one-device Dashboard redesign and governed map revision remain worthwhile, but should not displace the trust/data defects in this short window.

The planned DigitalOcean sprint remains separate. Before a public pilot, re-run browser journeys and server-side role/guest-link tests on the deployed build; this source review alone is not release acceptance.
